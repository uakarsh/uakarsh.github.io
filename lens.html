Lens: What's Actually Wrong With Your Model

Akarsh Upadhyay  ·  May 2026

The problem

When a model fails, the default workflow is: look at the accuracy number, squint at some confusion matrices, and guess what's wrong. Maybe run a few more epochs. Maybe try a different learning rate. The thing you rarely do is actually look at the failures in a structured way, because that's slow and it doesn't obviously scale.

The bigger issue is that model failures aren't all the same kind of thing. Some failures happen because the training data is bad — mislabeled images, ambiguous images that a human would also get wrong. Some happen because the model hasn't seen a particular visual pattern during training. And some happen because the task is genuinely hard for that architecture. These require completely different fixes, and treating them the same wastes a lot of time.

What Lens does

Lens is a small tool I built to make this analysis more systematic. The pipeline has a few stages:

Train and collect failures. Fine-tune a model, then collect every misclassification with the top-3 predictions and confidence scores. For the initial experiment I used ResNet-18 (ImageNet pretrained) on CIFAR-10, 3 epochs, no augmentation.

Generate hypotheses per failure. For each failure image, send it to a local vision-language model (qwen3-vl:8b via Ollama) and ask three specific questions: Is there a data quality issue here? What visual property caused the confusion? What augmentation or data change would help? The model gets the image plus the true label and predicted label as context. This runs locally — no external API calls, no data leaving the machine.

Cluster each dimension independently. Instead of treating the hypothesis as one blob of text, I split it into three separate dimensions and cluster each one independently using sentence embeddings (BAAI/bge-base-en-v1.5) and KMeans. The data quality dimension gets compressed to a one-sentence verdict before embedding — otherwise the cluster model just groups by which class pair was confused rather than what kind of data problem it is.

Review UI and dashboard. A FastAPI server with a simple UI for paging through failures, recording agree/disagree/skip verdicts, and looking at the cluster breakdowns for each dimension.

What we found on CIFAR-10

The model ended up at decent but uneven per-class accuracy. The two weakest classes were cat (61.9% F1) and dog (70.0% F1). The initial guess was overfitting — the val loss for these two classes rises after epoch 2. After trying dropout, two-phase freezing, and lower backbone LRs, and watching all of them hurt accuracy, the clearer explanation is that cat/dog boundary ambiguity is a property of the dataset, not a training problem. The model is doing about as well as it can given what the images look like.

The more useful result came from the error analysis on 150 sampled failures (15 per class). Of those, 84 were actionable data quality issues — 68 images a human would also struggle with (cropped so the key feature is missing, background texture bleeding into the object) and 16 that appear to be outright labeling errors. The other 66 were genuine model errors on reasonable images.

That split matters. If you're trying to improve this model, the first thing to do is fix the data, not the training. Sixteen mislabeled images per 150 failures is a high enough rate that cleaning the dataset will move accuracy more reliably than any training change.

The visual cause clusters gave a more concrete picture of what's hard:

14 failures: dark foreground objects hiding discriminative features. 9 failures: background texture matching object texture closely. 8 failures: ship hull cropped to expose only the lower portion, which looks like the underside of an airplane.

How this would work in production

The main overhead in the current setup is the VLM inference step — running qwen3-vl:8b locally on 150 images takes around 10–15 minutes on a laptop GPU. At production scale you'd want to run this on a subset of failures: sample a fixed number per class, run the analysis, and re-cluster periodically (daily or after each deployment).

The more important design question is what you do with the output. The annotation_issue tag is immediately actionable — those images are candidates for relabeling or removal and can be queued for a human review step without any additional analysis. The fix clusters are inputs to augmentation strategy for the next training iteration. The visual cause clusters are useful for debugging and for writing evaluation suites — if you know "partial occlusion by dark textured elements" is a failure mode, you can construct test cases that specifically stress that.

The human review UI is there to close the loop — a reviewer can quickly go through the sampled failures, mark which hypotheses are correct, and feed that signal back into the next round. Right now the verdicts are stored but not used to re-weight the clustering. That's one of the straightforward improvements.

What's next

The immediate next step is running a second training iteration with the augmentations from the fix clusters (head occlusion, background texture, crop augmentation) and comparing per-class F1 against the baseline. That's the direct test of whether the analysis actually translates to better model behavior.

A few other things that would make this more useful: using human review verdicts to filter noisy hypotheses before clustering; adding a comparison view between two training runs; and making it easier to add new datasets and model architectures without rewriting the pipeline. The current code is fairly tightly coupled to CIFAR-10 and ResNet-18.

The code is on GitHub. The experiment results — training logs, cluster assignments, and human feedback — are checked in alongside the scripts.
